3. The big items in detail

3.1 Shifts on mobile

What desktop does (from Domain/Shifts, Application/Shifts, Features/Shifts, migration 0009_shifts.sql): per-device shifts in three modes (Off, Auto at set times, Manual), opening cash carried over from the last close, expected cash = opening + cash sales + pay-ins − pay-outs − cash refunds, counted cash and difference, a needs count state for shifts that auto-closed, pay-in and pay-out with a reason, a top-bar chip, owner-only settings.

What the backend gives mobile: push mutations with these exact shapes (from docs/pos-pairing.md, "Task 7"):

  • shift.open {shop_id, opening_cash, opened_at, opened_by, origin, device_id?, note?}
  • shift.close {closed_at, closed_by, expected_cash, counted_cash?, note?} (no count means needs_count)
  • shift.count {counted_cash, expected_cash?, note?}. A counted shift is final.
  • cash_movement.create {shift_id, kind: pay_in|pay_out, amount, reason, occurred_at}
  • Cashiers may send these. Dashboard reads /api/v1/shifts/; the server recomputes expected cash and shows both numbers.

Mobile work: new SQLite tables (shifts, cash movements) plus a migration, a shift service in the same style as sale_service.dart (data + outbox in one transaction), outbox entries for the four mutation types, a shift screen and a status chip, settings read from the business row, and expected-cash maths copied from CashExpectation.cs (including the cash share of split sales and cancelled sales, issue #69).

Limitation to accept: shifts and cash movements are not in pull or bootstrap yet, so a reinstalled phone loses its shift history locally (the server keeps it). Phone and desktop in the same shop will each show only their own shifts.

3.2 Settings that must travel with the business

Receipt settings (footer, logo on/off, paper width) are business-level and owner-only in the backend. If mobile does not read them, the desktop prints one receipt and the phone prints another for the same shop. Printer name, copies and auto-print stay on each device.

4. Pairing: a question for you

"Pairing" can mean three different things here. Which one do you want on mobile?

  1. Code pairing like desktop. The owner shows a 6-digit code (or QR) from the dashboard, and a cashier's phone enters it and is linked with no OTP login. The backend is ready (/sync/pairing/redeem/ and /choose/, rate limits and device revoke included). Mobile work: a link screen, redeem, the merge or new-business choice, then the first upload. I recommend this if your goal is "cashier phones without the owner's login".
  2. Phone ↔ desktop over the local network. This is the "multi-device LAN feature" your desktop notes list as the next step, with its own ADR. It is a separate project: discovery, auth between devices, shared shift and stock view. It does not exist in the backend; it would be peer to peer.
  3. Printer pairing. Mobile already scans Bluetooth and network printers (features/devices). If you mean making that nicer, it is a small item.

Backend caveats for option 1: pairing tokens are normal user tokens for the owner's account (no step-up claim), a revoked device cannot re-register, and the desktop's own pairing has never run against a real server (desktop known issue #47). We should test both sides against the real backend together.

Two defects I found while reading the mobile receipt code (verified in source, not by running the app):
  • The PDF needs internet. sale_receipt_pdf_service.dart calls PdfGoogleFonts.notoSansRegular() and the Naskh variants. These download at runtime, so on a phone that is offline the receipt PDF fails. That breaks the offline-first rule for the one document a shop needs when the network is down.
  • English is hard-coded in the receipt sheet and thermal data. sale_receipt_sheet.dart writes 'Payment: ...', 'Ref: ...', 'Subtotal', 'TOTAL', 'Saved offline - pending sync' directly, so an Arabic user gets English on the shared text and on the printer.

5.3 Plan: draw once, output four ways

  1. One Flutter widget ReceiptPaper that is a line-by-line port of ReceiptVisual.Build: same widths (58 or 80 mm at 96 dpi), padding, sizes (17 / 15 / 12 / 11 / 10.5 / 10), colours (#111111 ink, #555555 grey), dashed rules, same rows and same order. Both languages, RTL, numbers always left to right with Latin digits, date dd MMM yyyy · HH:mm in the business time zone.
  2. Screen: the sale-complete sheet and sale detail show this widget.
  3. Share as image (what you asked for): wrap it in a RepaintBoundary, render at pixel ratio 3, share the PNG only, no text. Same helper as Baraka's sharePngFromWidget (utilities/sharing_utils.dart). That works for WhatsApp, Telegram, save to gallery.
  4. Share as PDF: the same rendered image placed on one page whose width equals the roll width and whose height fits the content. It matches the screen exactly because it is that picture. Trade-off: the text in the PDF cannot be selected or searched.
  5. Thermal print: send the same image as raster (ESC/POS bitmap) instead of text. Then Arabic prints properly and the paper looks like the screen. The existing text path stays as a fallback for printers that cannot take images.
For "100% the same", the font must be the same. Desktop draws the receipt in Segoe UI, a Windows font we cannot ship in the Flutter app. Without the same font, every width and line break differs slightly. Both apps already ship Geist and IBM Plex Sans Arabic (assets/fonts on mobile, DesignSystem/Fonts on desktop). Recommendation: change the desktop receipt to Geist (Latin) and IBM Plex Sans Arabic, then mobile uses the same files. This is a one-line font change in ReceiptVisual.cs, but it changes the printed look on the PC, so I will not touch the desktop repo unless you say so. It also removes the Google Fonts download.

5.4 Data the mobile receipt needs

The desktop Receipt record carries: business name, phone, logo bytes, currency, number, time, status, lines (name, qty, unit price, total, returned, discount), subtotal, discount, tax, net, payment method and parts, refunds, synced flag, customer name, what the customer owes, cashier name, tax name, tax rate, tax inclusive. Mobile has most of this in its local sale and refund tables; I expect gaps in cashier name, tax snapshot name/rate, split parts and customer balance not verified. Receipt strings (status names, "Owes now", "Returned", "Discount", tax labels, "Thank you") must be added to both app_en.arb and app_ar.arb with the same wording as the desktop resource file.

5.5 How we will prove it matches

  • Golden-image tests on mobile for the same fixed receipt data (English and Arabic, 58 and 80 mm, with and without discount, tax inclusive and added, split, on account, refunded).
  • Render the same fixtures on desktop (it already renders scenes to PNG in tests), put the two PNGs side by side, and diff them. You look at the pair and approve before I call it done.
  • I will not claim a match until that diff has been run; I cannot run the desktop app from here, so I will need the desktop PNGs from you or from your Windows machine.

6.3 Backend facts that affect both apps

  • Shifts, cash movements and debts are not in pull or bootstrap. Each device keeps its own copy and only the dashboard sees all of it (pos-pairing.md, "Still not done").
  • Cashiers can send shift.*, cash_movement.create and debt.payment. debt.writeoff is manager and above.
  • The server has no PIN. A staff PIN stays on the device (sync-contract-deviations.md 39).
  • Refund total is the line's share of the net amount (discount and tax included). Mobile and desktop must show the server's number in refund_total after sync.
  • seq and pruning: a device with no stored cursor must bootstrap first (item 18).
